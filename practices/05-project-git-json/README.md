## Цель и результат

В ПР № 4 мы написали консольный CRUD и интерфейс `TaskStore`, но все задачи исчезали при выходе. Здесь превратим программу в небольшой **проект из нескольких пакетов**, научимся хранить задачи в JSON-файле, управлять настройкой пути к файлу и проверять программу автоматическими тестами. Историю изменения кода зафиксируем в Git.

**Результат:** новая команда `cmd/task-cli-json` в **том же личном проекте `go-practice-01`**, сохраняющая задачи после перезапуска. Ранее созданную команду `cmd/task-cli` **не удаляем**. Для освоения материала используем [стартовый каркас](starter/README.md); [референсное решение преподавателя](examples/README.md) — отдельно, для разбора и самопроверки.

## 0. Подготовка: не создавайте второй модуль

Откройте **свой** каталог `go-practice-01`. В его корне уже должен быть `go.mod` из ПР № 1. Проверьте:

~~~bash
go version
go env GOMOD
git status
~~~

`go env GOMOD` должен показывать путь к `go.mod` личного проекта, а не `NUL` или `/dev/null`. Если `go.mod` ещё нет, восстановите инструкции [ПР № 1](../01-introduction/README.md); не запускайте `go mod init` в каждой подпапке.

Перенесите **содержимое** [`starter/`](starter/README.md) в корень своего проекта, сохраняя относительные пути. В случае вопросов о перезаписи проверьте, что новые файлы не заменяют решения ПР № 1–4. Получится:

~~~text
go-practice-01/
├── go.mod                         # уже существует, НЕ заменяем
├── cmd/
│   ├── task-cli/main.go           # ПР № 4, оставить как есть
│   └── task-cli-json/main.go      # новая программа
└── internal/
    ├── tasks/store.go             # модель и CRUD
    └── persistence/
        ├── json.go                # заглушки TODO
        └── json_test.go           # тесты для проверки
~~~

Материалы предполагают `module example.com/go-practice-01`, как в ПР № 1. Если в вашем `go.mod` другое имя, замените во **всех новых импортах** `example.com/go-practice-01` на значение после `module`. Импорт никогда не пишется как путь к папке Windows.

## 1. Пакеты и Go Modules

В ПР № 4 все типы находились в одном `package main`. В новой версии разделим обязанности:

| Путь | Пакет | За что отвечает |
|---|---|---|
| `cmd/task-cli-json/main.go` | `main` | Ввод и команды пользователя |
| `internal/tasks/store.go` | `tasks` | Модель `Task`, бизнес-правила, CRUD |
| `internal/persistence/json.go` | `persistence` | Чтение и запись состояния в файл |

`go.mod` задаёт **имя модуля** и версию языка, `package` — имя пакета исходного файла, `import` позволяет использовать опубликованные сущности другого пакета. В Go **экспортируются** имена с заглавной буквы: `tasks.Task` доступен извне, `tasks.nextID` — нет.

~~~go
import "example.com/go-practice-01/internal/tasks"

store := tasks.NewMemoryStore()
task, err := store.Add("Изучить Go", 2)
~~~

Папка `internal` означает, что пакеты доступны внутри родительского дерева модуля, но не внешним проектам. Сторонние зависимости в этой работе **не нужны**: используем стандартную библиотеку.

**Задание:** откройте три указанных файла и найдите импорт, создаваемую структуру и функцию `main`. Объясните, почему невозможно обращаться к `store.nextID` напрямую из `main`.

## 2. Что именно записываем в JSON

Наша модель задачи прежняя:

~~~go
type Task struct {
    ID       int    `json:"id"`
    Title    string `json:"title"`
    Status   string `json:"status"`
    Priority int    `json:"priority"`
}
~~~

Теги `json:"..."` задают имена полей в JSON; буквы `ID` и `Title` при этом остаются экспортируемыми именами Go. Для сохранения **уникальных ID после удаления** недостаточно сериализовать только список задач. Поэтому храним ещё счётчик:

~~~go
type State struct {
    NextID int    `json:"next_id"`
    Tasks  []Task `json:"tasks"`
}
~~~

Пример корректного файла:

~~~json
{
  "next_id": 3,
  "tasks": [
    {"id": 1, "title": "Изучить Go", "status": "done", "priority": 2},
    {"id": 2, "title": "Написать API", "status": "new", "priority": 3}
  ]
}
~~~

`json.MarshalIndent` преобразует значение Go в текст JSON с отступами; `json.Decoder.Decode` — обратно. Пустой файл **не равен** отсутствующему файлу: пустой файл содержит некорректный JSON, а отсутствие файла при первом запуске означает новое хранилище.

## 3. Реализуйте загрузку: `Load`

Откройте `internal/persistence/json.go` и реализуйте `Load(path string) (tasks.State, error)`. В каркасе сейчас заглушка: программа запускается, но сохранения ещё нет.

Алгоритм:

1. Прочитайте файл через `os.ReadFile(path)`.
2. Если `errors.Is(err, os.ErrNotExist)`, верните `tasks.State{NextID: 1}, nil`.
3. Другие ошибки чтения **не маскируйте** — верните их с контекстом через `fmt.Errorf("...: %w", err)`.
4. Преобразуйте байты в `tasks.State` с `json.NewDecoder`. Включите `DisallowUnknownFields()`.
5. Убедитесь, что в файле есть **ровно один** JSON-документ: второй вызов `Decode` должен завершиться `io.EOF`.
6. Вызовите `tasks.NewMemoryStore().Restore(state)`: метод проверяет ID, приоритет, статус, название, счётчик и дубликаты. При ошибке **не загружайте** повреждённые данные.

Ключевые элементы:

~~~go
data, err := os.ReadFile(path)
if errors.Is(err, os.ErrNotExist) {
    return tasks.State{NextID: 1}, nil
}
// дальше обработка прочих ошибок и декодирование
~~~

**Проверка:** в папке данных создайте намеренно некорректный файл `{oops`. Программа должна показать ошибку и не заменять его пустым списком. Верните файл к корректному состоянию перед следующей проверкой.

## 4. Реализуйте сохранение: `Save`

Функция `Save(path string, state tasks.State) error` должна:

1. Проверить `state` через `MemoryStore.Restore`, прежде чем записывать что-либо.
2. Преобразовать состояние в JSON с `json.MarshalIndent` и добавить перевод строки.
3. Создать временный файл **в той же папке**, что и целевой: `os.CreateTemp(filepath.Dir(path), ".tasks-*.tmp")`.
4. Записать байты, проверить ошибки `Write`, `Sync`, `Close`.
5. Заменить конечный файл через `os.Rename`; временный файл удалять в `defer` при ошибке.

**Почему не писать сразу в `tasks.json`?** Если запись оборвётся, файл может содержать половину JSON. Временный файл снижает вероятность порчи. Это **учебное** решение: оно не гарантирует транзакционность, защиту от конкурентной записи или одинаковую атомарность на всех файловых системах.

В `main.go` вызов `Save` уже стоит **после успешных** команд `Add`, `Complete`, `Delete`. При ошибке записи программа завершает работу и сообщает причину: продолжать изменения только в памяти было бы опасно. Не выполняйте сохранение после неуспешной команды.

## 5. Настройка пути через переменную окружения

В `cmd/task-cli-json/main.go`:

~~~go
path := os.Getenv("TASKS_FILE")
if path == "" {
    path = "tasks.json"
}
~~~

Путь относителен **текущей рабочей папке**, из которой запущена команда. Чтобы использовать другое имя файла:

**PowerShell (Windows):**

~~~powershell
$env:TASKS_FILE = "my-tasks.json"
go run ./cmd/task-cli-json
Remove-Item Env:TASKS_FILE
~~~

**Bash (Linux/macOS):**

~~~bash
TASKS_FILE=my-tasks.json go run ./cmd/task-cli-json
~~~

По умолчанию данные пишутся в `tasks.json` **в корне личного проекта**. Добавьте в его `.gitignore`:

~~~gitignore
/tasks.json
/my-tasks.json
*.tmp
~~~

Не коммитьте свои личные данные, пароли или реальные токены. `.gitignore` не удаляет уже отслеживаемые файлы из истории Git.

## 6. Первый табличный тест

Go выполняет файлы с именем `*_test.go` командой `go test`. Метод `t.TempDir()` даёт временную папку для каждого теста, не затрагивая личные файлы.

Откройте `internal/persistence/json_test.go`: там есть тест **сохранения и повторной загрузки**, тесты ошибок чтения и случая, когда файл отсутствует.

~~~go
func TestMissingFileIsNewStore(t *testing.T) {
    state, err := Load(filepath.Join(t.TempDir(), "absent.json"))
    if err != nil || state.NextID != 1 {
        t.Fatalf("got %+v, %v", state, err)
    }
}
~~~

*Табличный тест* перебирает наборы входных данных через `for` и `t.Run(name, ...)`. В `TestLoadScenarios` проверьте, почему пустой файл, два JSON-объекта подряд и повторяющиеся ID считаются ошибкой.

**Запуск из корня личного проекта:**

~~~bash
go test ./...
go test -v ./internal/persistence
go vet ./...
go build ./...
~~~

До реализации `Load` и `Save` тесты **должны не проходить** — это ожидаемая особенность каркаса. После завершения работы всё должно стать зелёным. Не меняйте тесты только ради того, чтобы скрыть ошибку реализации.

## 7. Git: сохраните новый этап в истории

Это **продолжение** репозитория ПР № 1, а не создание второго аккаунта или репозитория. Сначала проверьте, что `git status` показывает ожидаемые файлы, а `tasks.json` не попал в индекс.

~~~bash
git status
git diff
git add cmd/task-cli-json internal .gitignore README.md
git commit -m "feat: persist tasks to JSON and add tests"
git push
~~~

Если у вас ветка или способ публикации отличается, используйте правильное имя удалённой ветки. Команда `git push` сработает без аргументов, если настроена отслеживаемая ветка. Если нет — разберите сообщение Git и настройте upstream, не выполняйте `push --force`.

**На защите:** покажите `git log -3 --oneline` и объясните, какие файлы появились в новом коммите.

## Типичные ошибки

| Проявление | Причина / исправление |
|---|---|
| `package ... is not in std` | Неверный путь импорта; проверьте имя `module` |
| `go.mod file not found` | Команда запущена не из корня личного проекта |
| После перезапуска всё пусто | `Load`/`Save` оставлены заглушками или указан другой `TASKS_FILE` |
| После удаления ID повторяется | Сохраняется только список, забыли `next_id` |
| Неверный JSON затирается | Ошибка чтения была ошибочно принята за отсутствие файла |
| Тест изменил реальный файл | Вместо `t.TempDir()` задан общий `tasks.json` |
| `git push` не работает | Нет upstream, доступа или удалённого репозитория; ошибка Git подскажет причину |
